QA Fundamentals (intermediate depth)

A reference for quality assurance and software testing terminology and practices—beyond definitions, with enough depth for ~3 years of hands-on QA (test design, risk, automation trade-offs, release judgment). Use it for interviews, test planning, and conversations with developers, product, and stakeholders.

Core concepts

Term Definition
Quality Assurance (QA) Processes and activities that help ensure a product meets requirements and is fit for use. QA focuses on prevention and improvement across the whole lifecycle, not only on finding bugs at the end.
Quality Control (QC) Activities that check whether the product meets defined standards (e.g. executing tests, reviewing builds). QC is often part of QA but is more verification-oriented.
Software Testing Running the software (or reviewing it) to find defects and assess whether it behaves as expected.
Defect / Bug A flaw where the product does not match requirements, design, or reasonable user expectations.
Failure Observable incorrect behavior at runtime (often caused by a defect).
Error A human mistake (e.g. wrong code or wrong test data) that can lead to a defect.
Fault The underlying cause in code or design that may remain latent until triggered (error → fault → failure chain).

Quality vs testing: Testing provides information about quality; it does not “create” quality. QA owns process, standards, and release recommendations; QC/testing executes checks. At 3+ years, you should articulate what you tested, what you did not, and why (risk, time, constraints)—not “we tested everything.”

Seven principles of testing (ISTQB-style)

Use these to explain trade-offs in interviews and planning:

  1. Testing shows presence of defects, not their absence — Passing tests reduce risk; they do not prove correctness.
  2. Exhaustive testing is impossible — Prioritize by risk, usage, and change impact.
  3. Early testing saves time and money — Reviews, unit tests, and clarifying requirements before code is complete.
  4. Defect clustering — A small number of modules often contain most defects; focus regression and review there.
  5. Pesticide paradox — Repeating the same tests finds fewer new issues; evolve suites and explore.
  6. Testing is context-dependent — Safety-critical, fintech, and internal admin tools need different strategies.
  7. Absence-of-errors fallacy — A bug-free product that solves the wrong problem still fails validation.

Verification vs validation

Term Question it answers
Verification “Did we build it right?” — checking against specs, design, and standards (reviews, inspections, unit tests).
Validation “Did we build the right thing?” — checking that the product solves the real user or business need (UAT, beta, field trials).

Static vs dynamic: Static testing (reviews, walkthroughs, static analysis) finds defects without executing code. Dynamic testing runs the SUT. Both belong in a mature strategy.

SDLC vs STLC (where QA sits)

Phase (typical STLC) QA activities
Requirements analysis Review for testability, ambiguity, missing NFRs; draft high-level scenarios; RTM seeds.
Test planning Scope, approach, resources, risks, entry/exit criteria, automation strategy.
Test design Cases, data, charters; traceability to requirements/stories.
Environment setup Config, data, integrations, feature flags, access.
Execution Manual, automated, exploratory; logging evidence.
Closure Metrics, lessons learned, sign-off input, regression baseline updates.

STLC overlaps Agile sprints: planning/design/execute/report happen every iteration, not only once per project.

Types of testing (by scope)

Term Definition
Unit testing Tests the smallest testable pieces (functions, classes, modules), usually automated and run by developers.
Integration testing Tests how components work together (APIs, databases, services, UI + backend).
Component / service testing A single deployable unit in isolation with mocks for dependencies (common in microservices).
System testing Tests the complete, integrated application against requirements in an environment close to production.
End-to-end (E2E) testing Simulates real user flows across the full stack (often via browser or mobile automation).
Acceptance testing Confirms the system is acceptable for release; UAT (user acceptance testing) is done by business users or representatives.
Alpha / beta testing Controlled release to internal or external users before general availability.
Regression testing Re-running tests after changes to ensure existing behavior still works.
Smoke testing Quick, shallow check that critical paths work after a build or deploy (“is it worth deeper testing?”).
Sanity testing Narrow check on a specific fix or small area after a change.
Re-testing Re-run tests that failed after a fix (confirm the defect is resolved).
Confirmation testing Same idea as re-testing: verify a specific fix.

Test pyramid (practical view): Many fast unit tests, fewer integration/API tests, fewer still UI E2E tests—because E2E is slow, brittle, and expensive to maintain. Testing quadrants (Brian Marick): business-facing vs technology-facing × support development vs critique product—helps place manual exploration, UAT, unit tests, and performance work.

Types of testing (by knowledge of internals)

Term Definition
Black-box testing Testing based on inputs and expected outputs without looking at internal code structure.
White-box testing Testing with knowledge of internal logic, branches, and data paths (often structural or code-coverage driven).
Gray-box testing Partial knowledge of internals (e.g. schema, APIs, logs, DB state) combined with user-facing behavior.

Code coverage (white-box aid, not a goal by itself): Statement, branch, path, and condition coverage measure what code ran during tests. High coverage with weak assertions still misses bugs.

Test design techniques (apply these in daily work)

Technique When to use Idea
Equivalence partitioning Input fields, categories Split inputs into classes that should behave the same; pick one representative per class.
Boundary value analysis (BVA) Min/max limits, lengths, dates Test at, just below, and just above boundaries (often where off-by-one bugs live).
Decision table testing Business rules with combinations Rows = rule combinations; columns = conditions/actions; reduces missed rule pairs.
State transition testing Workflows (orders, auth, tickets) States, events, valid/invalid transitions; cover paths and guard conditions.
Pairwise / combinatorial Many configuration options Cover all pairs of parameters with fewer runs than full Cartesian product.
Use case / scenario testing End-user flows Main success path + alternates and exceptions from use cases or user stories.
Error guessing Experienced testers Based on past defects, common dev mistakes, and domain knowledge.

Example (BVA): Field allows 1–100 characters → test 0, 1, 100, 101 (and empty if allowed separately).

Ad hoc testing Informal testing without a formal plan (less repeatable than exploratory testing with a charter).

Boundary / edge testing Values at limits (min, max, just inside/outside boundaries).
Compatibility / cross-browser Rendering, APIs, and behavior across browsers, OS, devices.
Localization (L10n) / internationalization (I18n) Locales, formats, RTL, string length, legal text.

Risk-based testing (intermediate essential)

Risk ≈ likelihood × impact. Use it to choose depth, not to skip documentation.

Step Action
Identify Features, integrations, data, NFRs, areas of change.
Analyze What breaks? Who is affected? How often is it used?
Prioritize High risk → deeper tests, automation, pair with dev; low risk → smoke + spot checks.
Mitigate Tests, monitoring, feature flags, rollback plan.
Communicate Release notes, known issues, test summary for stakeholders.

Product risk vs project risk: Product risk = wrong behavior in production. Project risk = slip, env unavailable, missing requirements. QA reports both.

Term Definition

Load testing Behavior under expected load.
Stress testing Behavior beyond normal capacity until breaking point.
Spike testing Sudden traffic bursts.
Soak / endurance testing Sustained load over hours/days (memory leaks, connection pools).

Performance acceptance (examples): p95 latency under X ms at Y RPS; error rate < Z%; CPU/memory ceilings on staging that mirror prod ratio.

API and integration testing (depth)

Concept What to verify
Contract Request/response schema, required fields, enums, versioning (OpenAPI/Swagger).
HTTP semantics Correct status codes (200, 201, 400, 401, 403, 404, 409, 422, 500); idempotency for PUT/DELETE where applicable.
Auth Tokens, expiry, refresh, scope, negative cases (missing/invalid token).
Data integrity DB state after API calls; transactions; eventual consistency if async.
Dependencies Timeouts, retries, circuit breakers; behavior when downstream is down (mock or test doubles).
Negative / abuse Oversized payloads, injection in JSON fields, rate limits.

Tools mindset: REST clients (Postman, Insomnia), contract tests, service virtualization—not only UI automation.

Database testing (basics every QA should know)

  • CRUD operations match UI/API and business rules.
  • Constraints (unique, FK, NOT NULL) enforced; error messages acceptable.
  • Migrations — schema changes do not corrupt data; rollback tested when required.
  • Reports / aggregations — totals, filters, time zones, rounding.
  • Concurrency — duplicate submissions, locking (where relevant).
  • PII — masking in non-prod, access controls.

Use read-only queries in lower envs; never test destructive scripts against shared prod-like data without approval.

Good acceptance criteria (Agile): Specific, testable, independent of implementation (“user can reset password via email link within 15 minutes”) — ties to INVEST for stories (Independent, Negotiable, Valuable, Estimable, Small, Testable).

Defect lifecycle and triage (depth)

Term Definition
Severity Impact on the system or user (e.g. critical, major, minor).
Priority Order in which the team should fix it (business urgency).
Reproduce / steps to reproduce Exact steps to make the defect appear again.
Fixed / resolved Developer addressed the issue in a build.
Retest QA verifies the fix in a new build.
Regression (defect context) A fix or change broke something that worked before.
Closed / verified Fix confirmed; defect no longer open.
Deferred / won’t fix Accepted risk or postponed intentionally.
Duplicate / cannot reproduce Triage outcomes; document env and data when closing as NRR.
Root cause analysis (RCA) Why the defect escaped; action items (test gap, review, automation).

Situation Severity Priority
Crash on checkout for all users Critical P1
Typo on internal admin page Minor Low
Wrong tax calculation Critical P1
Cosmetic misalignment on rare screen Minor May be high if launch-blocking for marketing

Triage meeting: Dev, QA, PM align on priority, assignee, target release, and whether a workaround exists.

Automation and CI/CD

Term Definition
Test automation Scripts or tools that run tests without manual repetition.
Manual testing Human execution and judgment; essential for UX, exploration, and one-off checks.
CI (Continuous Integration) Frequent merges with automated builds and tests on each change.
CD (Continuous Delivery / Deployment) Automated path to release-ready or production builds (with gates).
Flaky test A test that sometimes passes and sometimes fails without a product change (timing, data, environment).
Test oracle Expected outcome or mechanism to decide pass vs fail.
Test double Mock, stub, fake, spy — replaces dependencies for isolated tests (mostly dev/unit; QA should understand limits of E2E with mocks).
Page Object Model (POM) UI automation pattern: encapsulate locators and actions per page/screen.
Data-driven testing Same test logic, multiple data sets (CSV, JSON, examples table).
Parallel execution Faster feedback; requires isolated data and stable env.
Shift-right Monitoring, canary, production smoke, synthetic checks after deploy.

What to automate (rule of thumb): Stable, high-value, repeated checks (regression, API contracts, critical paths). Avoid automating one-off experiments or constantly changing UI without stable selectors.

Flake mitigation: Explicit waits, stable test data, idempotent setup/teardown, quarantine flaky tests with tickets, never “rerun until green” without investigation.

Agile, BDD, and shift-left

Term Definition
Shift-left Doing testing and quality activities earlier (requirements, design, unit tests).
Three Amigos BA/PM, dev, QA align on story scope and examples before implementation.
Sprint / iteration testing Testing within short development cycles alongside new stories.
Definition of Ready (DoR) Story is clear enough to start (acceptance criteria, dependencies).
Definition of Done (DoD) Shared checklist before work is “done” (often includes tests, review, docs).
BDD (Behavior-Driven Development) Examples in Given/When/Then form to drive development and tests (e.g. Cucumber, Gherkin).

Refinement / grooming QA contributes testability and edge cases before sprint commitment.

Metrics (use with care)

Term Definition
Test coverage How much of requirements or code is exercised by tests (not a guarantee of quality).
Requirements coverage % of reqs/stories with at least one executed test.
Pass rate Percentage of tests passed in a run.
Defect density Defects per size of product (e.g. per story, module, or KLOC).
Defect leakage / escape rate Defects found in prod vs total (by severity).
Escape defect A defect found in production after release.
Mean time to detect (MTTD) / repair (MTTR) Ops/quality signals for production issues.
Automation ROI Time saved vs maintenance cost—track flaky rate and fix time.

Anti-patterns: Gaming pass rate by deleting failing tests; mandating 100% automation; using coverage alone as a release gate.

Entry and exit criteria (examples)

Entry criteria — conditions before testing starts (e.g. build deployed, test data ready, critical bugs from last cycle fixed, stories meet DoR, env parity documented).

Exit criteria — conditions to stop testing or approve release (e.g. planned tests executed, no open Sev-1/2 defects, regression pass on target build, NFR spot-checks done, UAT sign-off, rollback verified).

Suspension / resumption: Pause testing if env down or build unstable; resume when entry criteria met again.

Release readiness (what senior stakeholders ask)

  • Scope of this release vs what was tested (and not tested).
  • Open defects by severity/priority and business acceptance of known issues.
  • Regression scope and automation results (including flakes).
  • NFR status (performance, security scan results if applicable).
  • Rollback / feature-flag plan.
  • Monitoring and support handoff.

Communication and collaboration

  • Clear bug reports: One defect per ticket, neutral tone, reproducible steps, logs/screenshots, build/version, test account (non-PII in screenshots).
  • Dev collaboration: Reproduce together, agree on expected behavior vs spec gap, distinguish bug vs enhancement.
  • Product: Clarify acceptance criteria; escalate spec ambiguity as risk, not “user error.”
  • Documentation: Update test cases and charters when behavior intentionally changes.

Exploratory testing heuristics (quick reference)

Use mnemonics to avoid tunnel vision (e.g. SFDPOT — Structure, Function, Data, Platform, Operations, Time; or CRUCSPIC STMPL from HTSM for deeper tours). Combine with charters: “Explore payment refunds for 90 minutes focusing on error handling and partial refunds.”

Interview-ready one-liners (3-year level)

  • Difference QA vs QC: QA improves process; QC evaluates product against standards through testing and inspection.
  • When not to automate: Unstable UI, one-time checks, heavy visual judgment, cost of maintenance > manual cost.
  • How you prioritize: Risk (usage × impact), recent code change, history of defects in module, regulatory need.
  • Good test case: Clear preconditions, steps, data, expected result, traceable to requirement, maintainable.
  • What you do when requirements are vague: Ask questions, propose examples, document assumptions, test against agreed acceptance criteria, log spec gaps as defects or stories.

Further reading mindset

Good QA at intermediate level combines structured testing (plans, techniques, regression, traceability) with critical thinking (exploration, risk-based focus, clear release communication). Prioritize by risk, invest in API and integration depth, treat automation as software engineering (maintainable, reliable), and keep learning domain and NFR skills—not only UI flows.

Top 10 real-time interview questions (QA fundamentals)

Questions commonly asked in live interviews (~3 years experience), with concise answers you can expand with your own examples.

1. What is the difference between QA, QC, and testing?

Answer: Testing executes the product to find defects and gather information. QC is product-focused verification (testing, inspections) against standards. QA is process-oriented—it defines how the team prevents defects (standards, reviews, metrics, release gates). Testing is often part of QC; both support QA.

2. Explain verification vs validation with an example.

Answer: Verification: “Did we build it right?”—compare to spec (e.g. login accepts email format per design doc; code review passes). Validation: “Did we build the right thing?”—real need met (e.g. UAT shows users can complete onboarding faster; beta feedback confirms the feature solves the problem).

3. What is regression testing, and when do you run it?

Answer: Re-running existing tests after a change to ensure nothing broke. Run after bug fixes, new features in shared areas, refactors, env/config changes, and before release. Scope can be full regression or risk-based subset (smoke + modules touched + historically fragile areas).

4. How do severity and priority differ? Give an example where they don’t match.

Answer: Severity = technical/user impact of the defect. Priority = fix order for the business. Example: cosmetic logo wrong on a rarely used report—minor severity, but high priority if a major customer demo is tomorrow. Or: data corruption in a legacy module—critical severity, lower priority if module is disabled and no users affected.

5. What test design techniques do you use most often?

Answer: Equivalence partitioning and boundary value analysis for inputs; decision tables for business rules; state transition for workflows (orders, approvals); exploratory testing with charters when specs are incomplete. Mention one real bug you found using BVA or state transitions if asked to go deeper.

6. Smoke test vs sanity test vs regression—what’s the difference?

Answer: Smoke: broad, shallow “is this build testable?” on critical paths after deploy. Sanity: narrow check on one fix or small area (“does this ticket’s change work?”). Regression: broader re-check of previously working behavior after changes; can include many suites and automation.

7. What would you automate vs keep manual?

Answer: Automate: stable, repeated, high-value checks—API regression, critical E2E paths, data setup, contract tests. Manual: exploratory sessions, new/unstable UI, usability, one-off investigations, visual judgment. Balance test pyramid: many fast unit/API tests, fewer UI E2E. Maintain automation like product code (reviews, flake fixes).

8. How do you test when requirements are unclear or changing?

Answer: Clarify acceptance criteria with PM/dev (Three Amigos); document assumptions; use examples and edge cases; exploratory charters; log ambiguities as defects or stories. In Agile, tie tests to acceptance criteria on the story; retest when criteria change. Never silently guess—make risk visible to stakeholders.

9. What are entry and exit criteria for a test cycle or release?

Answer: Entry: build available, env stable, test data ready, known blockers from last cycle resolved, scope agreed. Exit: planned tests executed (or waived with sign-off), no open critical/high defects per policy, regression pass on release candidate, NFR spot-checks if in scope, UAT/sign-off as required. Suspension if env or build is unusable.

10. How do you write a good bug report?

Answer: One issue per ticket; clear title; steps to reproduce; expected vs actual; environment, build/version, browser/OS; test data (no real PII); logs, screenshots, HAR/video if useful; severity and priority with short rationale; mention if intermittent and what you tried. Goal: developer reproduces without ping-pong.

Bonus follow-ups interviewers often ask: difference between black-box and white-box; one principle of testing you rely on (#2 exhaustive testing impossible → risk-based); traceability (req → test → defect); difference between re-test and regression testing; what is a flaky test and how you handle it.

1. What is database testing?

Database testing verifies that data is stored, updated, retrieved, and deleted correctly according to business rules, schema, and application behavior.

You validate Examples
Schema Tables, columns, types, keys, indexes
CRUD operations Insert/update/delete reflected in DB
Constraints NOT NULL, UNIQUE, FK, CHECK
Business rules Order total = sum of line items
Migrations Upgrade scripts don’t corrupt data

Interview one-liner

Database testing confirms the persistence layer matches functional requirements—through SQL queries, constraints, and cross-checks with API/UI actions.

2. Why test at the DB layer?

  • UI can lie — green message but wrong row in DB
  • API tests can assert response JSON; DB checks prove persistence
  • Batch jobs / ETL often have no UI
  • Performance & reporting depend on correct aggregates

Test pyramid: Many unit tests (repo layer), integration tests (API + DB), fewer UI tests.

3. Types of database testing

Type Focus
Structural / schema Table design, normalization, indexes
Functional / CRUD App actions → correct rows
Non-functional Load, backup/restore, failover (often DBA + perf team)
Security SQL injection, least privilege, masking PII
Migration testing Flyway/Liquibase scripts on copy of prod-like data

4. SQL essentials for testers

SELECT — verify state

SELECT * FROM users WHERE email = 'test@example.com';
SELECT order_id, status, total FROM orders WHERE user_id = 42 ORDER BY created_at DESC;

COUNT / aggregates

SELECT COUNT(*) FROM cart_items WHERE cart_id = 100;
SELECT SUM(amount) FROM payments WHERE order_id = 5001;

JOIN — relational checks

SELECT o.id, o.status, u.email
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.id = 9001;

INSERT / UPDATE / DELETE (test setup & cleanup)

INSERT INTO users (email, role) VALUES ('qa+1@test.com', 'USER');
UPDATE products SET stock = stock - 1 WHERE sku = 'ABC';
DELETE FROM sessions WHERE user_id = 99;

6. CRUD and API + DB validation

Pattern: Act via API/UI → assert HTTP/UI → confirm DB.

Timing: Use transaction visibility rules—read after commit; in tests, poll DB briefly if async writes.

8. Common scenarios to test

  1. Boundary values — min/max length, zero quantity, max int
  2. Duplicate submission — double-click Pay → one charge
  3. Concurrency — two users buy last item (locking / optimistic concurrency)
  4. Timezone & dates — created_at UTC vs display
  5. Unicode & collation — names with accents, emoji in text fields
  6. Soft delete — row hidden in UI but still in DB with deleted_at
  7. Audit columns — created_by, updated_at on change
  8. Reporting totals — match sum of detail rows
  9. Migration rollback — downgrade script restores schema/data
  10. Null handling — optional fields, outer joins in reports

10. 15 interview Q&A

Q1. Difference between UI test and database test?
A: UI validates display and flows; DB testing validates persisted state, constraints, and data rules directly—often more precise for backend bugs.

Q2. How do you verify a user was created after API signup?
A: POST signup → assert 201 → SQL SELECT by email → check columns (role, created_at, password not plaintext).

Q3. What is a foreign key?
A: Column referencing primary key of another table; enforces referential integrity (no orphan child rows).

Q4. How find duplicate emails in a table?
A: SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

Q5. What is SQL injection?
A: Untrusted input concatenated into SQL; attacker runs arbitrary SQL. Prevent with parameterized queries/prepared statements.

Q6. White box vs black box DB testing?
A: White box uses schema/code knowledge (triggers, stored procs); black box validates via app behavior and SQL outcomes without reading implementation.

Q7. How test DELETE cascades?
A: Create parent + children → delete parent → assert children removed or soft-deleted per design.

Q8. What is normalization?
A: Organizing tables to reduce redundancy (e.g. store customer once, reference by id in orders)—testers check anomalies (update anomalies) if denormalized.

Q9. How handle test data in parallel CI?
A: Unique keys per worker, isolated schemas, or container per job; avoid shared mutable accounts.

Q10. Difference between TRUNCATE and DELETE?
A: DELETE removes rows (can WHERE, triggers fire); TRUNCATE fast full table clear (DDL-like, often no row triggers)—know env policies before using in tests.

Q11. How validate ETL/load job?
A: Row counts source vs target, checksum/hashes, sample row comparison, null and key integrity checks.

Q12. What is an index? Why care in testing?
A: Speeds queries; wrong missing index = perf issue. Functional tests still pass—perf tests catch separately.

Q13. How test stored procedures?
A: Set up input rows → CALL proc → assert output result set and side effects on tables.

Q14. ACID properties?
A: Atomicity, Consistency, Isolation, Durability—transactions either fully apply or roll back; important for payment/order tests.

Q15. When would you not automate DB checks?
A: One-off exploratory, huge data diff needing human judgment, or when API contract tests + unit tests at repo layer already cover persistence adequately.

1. What is API testing?

API testing validates the application programming interface (backend) without the UI (or with minimal UI).

You verify Examples
Correctness Response body matches schema; fields have expected values
Status codes 200, 201, 400, 401, 404, 500
Contracts Request/response JSON structure, required fields
Business rules Cannot order with negative quantity
Performance (sometimes) Response time under SLA
Security (basics) Auth required, no data leak without token

Why APIs before UI?

  • Faster and more stable than UI tests
  • Failures pinpoint service layer
  • Test pyramid: many API tests, fewer UI E2E

Interview one-liner

API testing validates backend services directly via HTTP requests, checking status codes, response body, headers, and business logic—usually faster and more reliable than UI-only coverage.

2. HTTP fundamentals (must know)

Request structure

METHOD /path?query=value HTTP/1.1
Headers: Authorization, Content-Type, Accept, ...
Body: JSON / XML / form data (optional)

HTTP methods (REST)

Method Typical use Safe? Idempotent?
GET Read resource Yes Yes
POST Create / action No No
PUT Replace entire resource No Yes
PATCH Partial update No No
DELETE Remove resource No Yes

Idempotent: Same request repeated → same final server state (e.g. DELETE twice: second may 404, resource still gone).

POST vs PUT (classic example)

POST /orders with body { "item": "book" }

Call Result
Call 1 order #1
Call 2 order #2

→ Not idempotent — each call can create a new order (new side effect).

PUT /users/101 with body { "name": "Ana" }

Call Result
Call 1 name = Ana
Call 2 name = Ana

→ Idempotent — repeating the request leaves the resource in the same final state.

Why it matters for testing: Safe to retry GET, PUT, DELETE on network errors; blind POST retries can duplicate data unless the API uses an idempotency key.

Status codes (memorize by class)

HTTP status codes are three-digit numbers. The first digit is the class:

Class Range Meaning
2xx 200–299 Success — request succeeded
3xx 300–399 Redirect — client should go to another URL
4xx 400–499 Client error — bad request, auth, or not found
5xx 500–599 Server error — backend or gateway failed

2xx — Success

Code Meaning Typical use in API tests
200 OK GET success, PUT/PATCH update success
201 Created POST created a new resource (often Location header)
204 No Content Success with empty body (common DELETE, some PUT)

Also exist: 202 Accepted (async job started), 206 Partial Content (ranges) — mention if asked.

3xx — Redirect

Code Meaning API testing note
301 Moved Permanently Old URL permanently replaced
302 Found (temporary redirect) Common after login or HTTP→HTTPS
304 Not Modified Caching — client can use cached copy

REST JSON APIs often return 200/201 directly; redirects show more in browsers or legacy endpoints. In Postman, follow redirects is usually on (Settings).

4xx — Client error

Code Meaning Typical test scenario
400 Bad Request Malformed JSON, missing required field, wrong type
401 Unauthorized No token, expired/invalid credentials
403 Forbidden Authenticated but not allowed (role/permission)
404 Not Found Wrong path or resource ID does not exist
409 Conflict Duplicate email, version conflict, state conflict
422 Unprocessable Entity Valid JSON but business/semantic validation failed
429 Too Many Requests Rate limit exceeded — retry after delay / backoff

401 vs 403 (interview favorite): 401 = “who are you?”; 403 = “I know you, you can’t do this.”

5xx — Server error

Code Meaning Typical meaning
500 Internal Server Error Unhandled exception in app
502 Bad Gateway Proxy/gateway got invalid response from upstream
503 Service Unavailable Overload, maintenance, dependency down
504 Gateway Timeout Upstream too slow

In tests: 4xx often = expected for negative cases; 5xx usually = defect or environment issue (unless testing resilience).

Important headers

Header Purpose
Content-Type Body format (application/json)
Accept Expected response format
Authorization Bearer token, Basic auth
Cookie Session-based auth
X-Request-ID Tracing (sometimes)

JSON basics for assertions

{
  "id": 101,
  "name": "Galaxy",
  "active": true,
  "tags": ["a", "b"]
}

Paths: id, tags[0], nested user.email.

6. Postman advanced (scripts, CI)

Tests tab (assertions) — Chai via pm.test

Postman uses Chai assertion library in JavaScript.

// Status
pm.test("Status is 200", function () {
    pm.response.to.have.status(200);
});

// Response time
pm.test("Response time < 500ms", function () {
    pm.expect(pm.response.responseTime).to.be.below(500);
});

// JSON body
pm.test("User has email", function () {
    const json = pm.response.json();
    pm.expect(json.data.email).to.eql("george.bluth@reqres.in");
});

// Header
pm.test("Content-Type is JSON", function () {
    pm.response.to.have.header("Content-Type");
    pm.expect(pm.response.headers.get("Content-Type")).to.include("application/json");
});

Parse JSON safely

const body = pm.response.json();
pm.expect(body.id).to.be.a("number");
pm.expect(body.name).to.exist;

11. 30 interview Q&A

1. What is API testing?
Testing backend interfaces via HTTP (or other protocols) without UI, validating status, body, headers, and rules.

2. Difference GET vs POST?
GET reads (no body typically); POST creates/submits with body; POST not idempotent.

3. What is idempotent?
Repeating request doesn’t change final state beyond first apply — PUT, DELETE idempotent; POST not. Example: POST /orders twice → two orders; PUT /users/101 with { "name": "Ana" } twice → name still Ana.

4. 401 vs 403?
401 not authenticated; 403 authenticated but forbidden.

5. 200 vs 201?
200 OK general success; 201 resource created (often POST).

6. What is REST?
Architectural style: resources, URLs, HTTP methods, stateless, JSON representations.

7. What is Postman?
Client to send HTTP requests, organize collections, assert responses, environments, CI via Newman.

8. Environment variables in Postman?
{{var}} for base URL, tokens, IDs; switch dev/qa/prod environments.

9. How assert in Postman?
Tests tab: pm.test, pm.expect, pm.response.to.have.status().

10. How save token from login?
Tests tab: pm.environment.set("token", pm.response.json().token).

11. What is Newman?
CLI to run Postman collections in CI/CD.

12. Pre-request Script vs Tests?
Pre-request: before send (setup). Tests: after response (assert).

13. How test negative case?
Send invalid body/missing auth; expect 400/401/404.

14. What headers for JSON API?
Content-Type: application/json, often Accept: application/json.

15. Query param vs path param?
Path identifies resource (/users/1); query filters (?status=active).

16. What is OpenAPI/Swagger?
Machine-readable API spec; import to Postman.

17. How do you organize collections?
Folders by feature (Users, Orders); smoke vs regression; naming convention.

18. API test pyramid?
Many unit/API tests, fewer UI E2E.

19. How check performance in Postman?
Response time in UI; pm.response.responseTime in tests; load tools for serious perf.

20. Cookie-based session in Postman?
Login request; cookies stored; subsequent requests same domain.

21. Bearer token?
Authorization: Bearer <JWT>.

22. What is JSON Schema validation?
Validate response structure/types against schema.

23. Difference PUT vs PATCH?
PUT full replace; PATCH partial update.

24. 204 status?
Success with no response body (common DELETE).

25. How debug failing API test?
Status, body error message, headers, compare with curl/Postman Console, logs, env variables.

26. Collection Runner vs Newman?
Runner: GUI bulk run; Newman: CLI for automation.

27. Global vs collection variables?
Scope: global all collections; collection only that collection.

28. What is mock server in Postman?
Returns canned responses when backend unavailable.

29. REST Assured vs Postman?
REST Assured: tests in Java code, versioned with app; Postman: faster for exploration + Newman.

30. Example test cases for POST /users?
Valid create 201; missing email 400; duplicate 409; unauthorized 401; verify response fields and DB/list GET if access.

What is Selenium?

Open-source browser automation. Your code drives a real browser (Chrome, Firefox, Edge, Safari) via the W3C WebDriver protocol.

4. Waits

UI loads asynchronously — wait for state, not arbitrary time. Selenium does not auto-wait (unlike Playwright).

Type What it does When to use
Explicit wait Poll until a specific condition is true (max N seconds) Default choice
Implicit wait On every findElement, retry for up to N seconds if element missing OK as a small safety net, not your main strategy
Fluent wait Explicit wait with custom poll interval and ignored exceptions Same family as explicit; use when you need tuning
Thread.sleep / fixed pause Blind delay Avoid — slow, flaky, hides real bugs

Explicit wait — WebDriverWait + ExpectedConditions

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(15));
WebElement btn = wait.until(ExpectedConditions.elementToBeClickable(By.id("submit")));
btn.click();

await driver.wait(until.elementLocated(By.css('#submit')), 15000);

Common conditions: presenceOfElementLocated (in DOM) · visibilityOfElementLocated (shown) · elementToBeClickable (before click) · invisibilityOfElementLocated (spinner) · frameToBeAvailableAndSwitchToIt (iframe first).

Implicit wait

driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(2));

Does not wait for clickable, text change, or spinner gone. Can stack with explicit waits — many teams set 0 and use explicit only.

Fluent wait

new FluentWait<>(driver)
    .withTimeout(Duration.ofSeconds(30))
    .pollingEvery(Duration.ofMillis(200))
    .ignoring(NoSuchElementException.class);

Quick fixes

  • Stale element: DOM re-rendered → re-find inside until.
  • Flaky test: frame context → right condition → stable locator (don’t only increase timeout).
  • SCC/ODT: iframe → section visible → after Apply, spinner invisible or save toast.

8. Test framework & design patterns

Selenium is not a test framework – pair with TestNG/JUnit (Java) or pytest (Python).

TestNG basics (Java)

TestNG (“Test Next Generation”) is a Java test runner: it executes methods, records pass/fail, and produces reports. WebDriver opens the browser; TestNG runs and asserts your tests.

Maven dependency (know for interviews)

<dependency>
  <groupId>org.testng</groupId>
  <artifactId>testng</artifactId>
  <version>7.10.2</version>
  <scope>test</scope>
</dependency>

Run from command line: mvn test (Surefire plugin picks up TestNG tests).

Core annotations

Annotation When it runs Typical Selenium use
@Test Each test method Your scenario (login, search, …)
@BeforeMethod Before each @Test new ChromeDriver(), open base URL
@AfterMethod After each @Test Screenshot on fail, driver.quit()
@BeforeClass Once before all tests in class Heavy one-time setup
@AfterClass Once after all tests in class Cleanup shared resources
@BeforeSuite / @AfterSuite Start/end of XML suite Global config
@Parameters Injects parameters into test URL, user from XML or provider
@DataProvider Supplies data to test Multiple rows (users, browsers)

Order: @BeforeSuite → @BeforeClass → @BeforeMethod → @Test → @AfterMethod → @AfterClass → @AfterSuite.

Assertions (org.testng.Assert)

import org.testng.Assert;

Assert.assertEquals(actual, expected);
Assert.assertEquals(actual, expected, "optional message");
Assert.assertTrue(driver.getTitle().contains("Home"));
Assert.assertFalse(condition);
Assert.assertNotNull(element);

Failed assertion = test failed; remaining steps in that method may still run unless you stop explicitly.

Minimal Selenium + TestNG class

import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.Assert;
import org.testng.annotations.AfterMethod;
import org.testng.annotations.BeforeMethod;
import org.testng.annotations.Test;

import java.time.Duration;

public class LoginTest {

    private WebDriver driver;

    @BeforeMethod
    public void setUp() {
        driver = new ChromeDriver();
        driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
    }

    @AfterMethod
    public void tearDown() {
        if (driver != null) {
            driver.quit();
        }
    }

    @Test(description = "Valid user can log in")
    public void validLogin() {
        driver.get("https://www.saucedemo.com/");
        driver.findElement(By.id("user-name")).sendKeys("standard_user");
        driver.findElement(By.id("password")).sendKeys("secret_sauce");
        driver.findElement(By.id("login-button")).click();
        Assert.assertTrue(driver.getCurrentUrl().contains("inventory"));
    }
}

15. 30 interview questions with answers

Fundamentals (1–10)

1. What is Selenium WebDriver?
API that controls browsers via W3C WebDriver protocol using a browser-specific driver.

2. Name Selenium components.
WebDriver, Grid, IDE; RC is obsolete.

3. Difference between findElement and findElements?
One element (throws if none) vs list (empty if none).

4. List locator types.
id, name, className, tagName, linkText, partialLinkText, cssSelector/css, xpath.

5. Locator priority?
id/data-testid → name → CSS → XPath; avoid brittle absolute XPath.

6. quit() vs close()?
quit = end session; close = current window only.

7. Is Selenium a test framework?
No – use TestNG/JUnit/pytest for assertions and structure.

8. What is Selenese?
IDE command language (open, click, type).

9. What language bindings do you know?
Java, JavaScript (Node selenium-webdriver); concepts same across languages.

10. What is a browser driver?
Executable (e.g. ChromeDriver) that translates WebDriver commands to the browser.

Waits & sync (11–15)

11. Implicit vs explicit wait?
Implicit: global findElement retry. Explicit: wait for a specific condition (visible, clickable, spinner gone) — preferred for dynamic UI; keep implicit 0 or short.

12. Why avoid Thread.sleep?
Not tied to app state; flaky and slow — use ExpectedConditions or custom until.

13. What is StaleElementReferenceException?
Element left the DOM after re-render; re-locate with a fresh find/until.

14. When use elementToBeClickable?
Before click() when the control must be visible and enabled.

15. What is FluentWait?
Explicit wait with custom poll interval and ignored exceptions while polling.

Locators & DOM (16–20)

16. CSS vs XPath?
CSS: fast, attributes. XPath: text, axes, parent traversal.

17. How handle dynamic IDs?
Partial attributes, data-testid, CSS contains, relative XPath – not index-only paths.

18. How upload a file?
sendKeys(absolutePath) on <input type="file">.

19. Shadow DOM?
May need getShadowRoot() (Selenium 4) or pierce selectors.

20. Relative locators (Selenium 4)?
Locate element above/below/near another element.

Framework & design (21–25)

21. What is POM?
Page classes hold locators and actions; tests stay thin.

22. Benefits of POM?
Maintainability, reuse, single place to update UI changes.

23. How run tests in parallel?
TestNG parallel + one driver per thread (ThreadLocal).

24. How manage test data?
Data providers, JSON/Excel, env-specific config; no secrets in repo.

25. Screenshot on failure?
TakesScreenshot → getScreenshotAs; attach to report in @AfterMethod.

Advanced & comparison (26–30)

26. Actions class use cases?
Hover, drag-drop, context menu, key combinations.

27. When use JavaScriptExecutor?
Scroll into view, JS click when intercepted, read DOM properties.

28. What is Selenium Grid?
Hub routes tests to remote nodes for parallel/cross-browser execution.

29. Selenium vs Playwright?
Selenium: mature, multi-language, you manage waits. Playwright: auto-wait, strong tracing; both valid for E2E.

30. How fix a flaky test?
Root cause: locator stability, wait condition, test data isolation, iframe context; avoid increasing sleep.

3. W3C WebDriver protocol

W3C = World Wide Web Consortium — the international standards body for the web (HTML, CSS, accessibility, and APIs such as WebDriver).

What it is

  • An HTTP-based standard to automate web browsers (navigate, find elements, click, type, get text, etc.).
  • Former ecosystem name: Selenium; the protocol is now a W3C recommendation.
  • Browser vendors implement it via drivers (e.g. ChromeDriver, GeckoDriver).

What it is NOT (in your company wording)

  • Not necessarily the selenium-java Maven dependency.
  • At DS, the JavaScript client for that protocol in Cheetah web tests is Leadfoot.

Interview bullets

  • Standard client ↔ driver ↔ browser model.
  • Same ideas as Selenium interviews: locators, synchronization, sessions, multiple windows/frames.
  • iframes (Platform Management → Search) = same switchTo concept, exposed through Leadfoot/Cheetah API.

One-liner

“We automate web UI through the W3C WebDriver protocol; Leadfoot is our JavaScript binding, inside Cheetah.”

4. Leadfoot API (primary — most asked)

What it is

  • JavaScript client for the W3C WebDriver protocol — this is what you import/use in specs and Page Objects (via Cheetah’s binding).
  • Fluent, promise-based API — chain find → act → assert on one session.
  • Primary layer for web automation at DS (not selenium-java).

Conceptual PO pattern (what you actually write)

1. What is CI/CD?

CI (Continuous Integration) means developers merge code into a shared branch frequently. Each merge triggers automated build and test so bugs surface early.

CD usually means one of:

Term Meaning

Continuous Deployment Every change that passes the pipeline automatically goes to production.

Why it matters: faster feedback, fewer integration surprises, repeatable releases, and safer deployments.

Developer → Commit → CI (build, test, scan) → CD (staging → production)

2. Core concepts (basic)

Pipeline

A pipeline is an automated sequence of stages and steps (compile, test, package, deploy).

Stage vs job vs step

Level Meaning Example
Stage Logical phase Build → Test → Deploy
Job Runnable unit (often parallel) unit-tests, lint
Step Single command or action npm test, docker build

Artifact

Output saved between stages: JAR, Docker image, dist/ folder, test reports.

Trigger

What starts the pipeline:

  • Push or pull request
  • Tag (e.g. v1.0.0)
  • Schedule (cron)
  • Manual (workflow_dispatch)

Environment

Named target with config and secrets: development, staging, production.

Idempotency

Running the same pipeline twice with the same input should produce the same intended result (important for deploy scripts).

Fail fast

Run cheap checks (lint, unit tests) before slow steps (E2E, deploy) to save time and cost.

3. CI/CD pipeline anatomy

Typical flow for a web app:

┌─────────┐   ┌─────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐
│ Checkout│ → │  Lint   │ → │   Test   │ → │  Build  │ → │  Deploy  │
└─────────┘   └─────────┘   └──────────┘   └─────────┘   └──────────┘
                  │               │              │
                  └───────────────┴──────────────┴── fail → stop pipeline

Common stages:

  1. Source — clone repo, cache dependencies
  2. Build — compile / bundle
  3. Test — unit, integration, E2E
  4. Security — SAST, dependency scan, secrets scan
  5. Package — Docker image or zip
  6. Deploy — Kubernetes, VM, GitHub Pages, AWS

4. GitHub Actions

GitHub Actions is CI/CD built into GitHub. Workflows live in .github/workflows/*.yml.

Key terms

Term Description
Workflow YAML file defining automation
Event push, pull_request, schedule, etc.
Job Runs on a runner (Ubuntu, Windows, macOS)
Step Shell command or Action (reusable unit from Marketplace)
Matrix Run same job with multiple versions (Node 18, 20, 22)

Minimal example

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
      - run: npm ci
      - run: npm test
      - run: npm run build

Deploy to GitHub Pages (pattern)

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4

Secrets and environments

  • Secrets: Settings → Secrets and variables → Actions (e.g. AWS_ACCESS_KEY_ID)
  • Reference: ${{ secrets.MY_SECRET }}
  • Environments: add protection rules (required reviewers) before production deploy

Reusable workflows

Call a shared workflow from another repo or workflow:

jobs:
  call-workflow:
    uses: org/repo/.github/workflows/reusable-ci.yml@main

Caching

Speed up installs:

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}

When to use GitHub Actions

  • Project is on GitHub
  • You want zero separate CI server maintenance
  • Good fit for open source and small-to-medium teams

5. Jenkins

Jenkins is a self-hosted automation server. You install plugins, create jobs or pipelines, and run them on agents (executors).

Key terms

Term Description
Controller Central Jenkins server (schedules jobs)
Agent / Node Machine that runs build steps
Job (Freestyle) UI-configured build
Pipeline Jenkinsfile (code as pipeline)
Plugin Git, Docker, Kubernetes, Slack, etc.
Credential Stored secrets in Jenkins

Declarative pipeline example

pipeline {
    agent any

    triggers {
        pollSCM('H/5 * * * *')  // or webhook from Git
    }

    environment {
        NODE_VERSION = '20'
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }
        stage('Install') {
            steps {
                sh 'npm ci'
            }
        }
        stage('Test') {
            steps {
                sh 'npm test'
            }
        }
        stage('Build') {
            steps {
                sh 'npm run build'
            }
        }
        stage('Deploy') {
            when {
                branch 'main'
            }
            steps {
                sh './deploy.sh'
            }
        }
    }

    post {
        success {
            echo 'Pipeline succeeded'
        }
        failure {
            echo 'Pipeline failed'
        }
    }
}

Jenkins architecture (typical)

Git (webhook) → Jenkins Controller → assigns → Agent (Docker/K8s/VM)
                      ↓
                 Jenkinsfile
                      ↓
              stages: build → test → deploy

When to use Jenkins

  • On-prem or strict compliance requirements
  • Heavy customization and many legacy integrations
  • Large orgs with dedicated DevOps maintaining controllers and agents

6. GitHub Actions vs Jenkins

Aspect GitHub Actions Jenkins
Hosting GitHub-hosted or self-hosted runners Self-hosted (you manage)
Config YAML in repo Jenkinsfile + UI
Setup Low for GitHub repos Higher (server, plugins, upgrades)
Cost Free minutes; paid for private/high usage Infra + maintenance cost
Ecosystem GitHub Marketplace actions Huge plugin library

8. Advanced topics

Deployment strategies

Strategy Idea Risk
Rolling Replace instances gradually Medium
Blue/Green Two identical envs; switch traffic Low downtime
Canary Small % of users get new version Low blast radius
Feature flags Decouple deploy from release Operational complexity

GitOps

Git is the source of truth for desired state (Kubernetes manifests). Tools like Argo CD or Flux reconcile cluster state with Git.

PR merge → CI builds image → updates manifest in Git → CD tool syncs cluster

Pipeline security (DevSecOps)

  • SAST — static code analysis
  • SCA — dependency vulnerabilities (npm audit, Dependabot)
  • Container scan — Trivy, Snyk on Docker images
  • Secrets scanning — prevent keys in Git
  • OIDC to cloud — avoid long-lived cloud keys in CI (GitHub → AWS/GCP/Azure)

Observability after deploy

  • Health checks and smoke tests post-deploy
  • Rollback on error rate or latency SLO breach
  • Link deploy events to monitoring (Datadog, Prometheus)

Monorepo CI

  • Path filters — only run jobs when relevant folders change
  • Affected projects — Nx, Turborepo, Bazel

Self-hosted runners

GitHub Actions or Jenkins agents inside your VPC for access to private resources (internal APIs, artifactory).

9. Best practices

  1. Keep pipelines fast — cache deps, parallelize independent jobs.
  2. One pipeline per repo (or clear monorepo rules).
  3. Never commit secrets — use vault, Jenkins credentials, GitHub Secrets, OIDC.
  4. Immutable artifacts — tag builds with commit SHA; deploy that artifact.
  5. Reproduce locally — same commands as CI in package.json scripts / Makefile.
  6. Fail loudly — notifications on main failures (Slack, email).
  7. Document rollback — automated or one-command rollback path.
  8. Separate CI from CD permissions — production deploy role is minimal.
  9. Review workflow changes — .github/workflows changes need code review too.
  10. Test the pipeline — use PRs to validate workflow edits.

10. 20 CI/CD interview questions

Basic (1–7)

Q1. What is the difference between Continuous Integration and Continuous Delivery?
A: CI merges code often and runs automated build/test on each integration. Continuous Delivery keeps the app always deployable; production release is a controlled (often manual) step after CI passes.

Q2. What triggers a typical CI pipeline?
A: Git events (push, PR), tags, schedules, or manual runs. Webhooks connect Git hosts to Jenkins or GitHub Actions.

Q3. What is an artifact in CI/CD?
A: A durable output from a build stage (binary, Docker image, zip, test report) passed to later stages or stored in a registry.

Q4. Why do we run tests in CI?
A: To catch regressions early, block broken merges, and give confidence before deploy. Required checks enforce quality on protected branches.

Q5. What is a failed pipeline “fail fast”?
A: Ordering cheap steps (lint, unit tests) before expensive ones (E2E, deploy) so failures stop the pipeline quickly and save time/cost.

Q6. What is branch protection?
A: GitHub/GitLab rules requiring reviews, passing CI, or signed commits before merging to main.

Q7. What is the difference between a job and a step in GitHub Actions?
A: A job runs on one runner and can contain multiple steps. Steps are individual tasks (checkout, run script, use an action). Jobs in the same workflow can run in parallel unless needs defines order.

Intermediate (8–14)

Q8. How do you store secrets in GitHub Actions vs Jenkins?
A: GitHub: encrypted Secrets and Environments, referenced as ${{ secrets.NAME }}. Jenkins: Credentials plugin bound to jobs; inject via withCredentials or environment. Never log secrets; mask in output.

Q9. Explain blue/green deployment.
A: Two identical environments (blue=live, green=new). Deploy new version to green, test, switch traffic/router to green. Rollback = switch back to blue.

Q10. What is a Jenkinsfile and why use Pipeline as Code?
A: A Jenkinsfile defines the pipeline in Groovy (Declarative or Scripted). It is versioned with the app, reviewable in PRs, and reproducible across branches.

Q11. How would you speed up a slow Node.js CI pipeline?
A: Cache node_modules or npm cache, use npm ci, run lint/unit in parallel jobs, matrix only when needed, skip jobs with path filters, use smaller runners or self-hosted for heavy work.

Q12. What is OIDC in GitHub Actions for AWS?
A: Short-lived tokens via id-token: write and aws-actions/configure-aws-credentials — no static AWS keys in secrets. Preferred for cloud deploy from CI.

Q13. What is the purpose of needs in GitHub Actions?
A: Defines job dependencies so job B runs only after job A succeeds — creates stage ordering and DAG workflows.

Q14. How do you deploy only from the main branch?
A: GitHub Actions: if: github.ref == 'refs/heads/main' on deploy job, or environment protection. Jenkins: when { branch 'main' } in deploy stage.

Advanced (15–20)

Q15. Compare canary vs rolling deployment.
A: Rolling updates instances in batches until all are new. Canary routes a small traffic slice to the new version, monitors metrics, then expands or rolls back. Canary reduces blast radius; rolling is simpler infra.

Q16. What is GitOps and how does it relate to CI/CD?
A: GitOps uses Git as the single source of truth for infrastructure/app state. CI builds and publishes artifacts; CD (Argo CD/Flux) syncs cluster state from Git. Separates “build” from “reconcile desired state.”

Q17. How do you secure a CI/CD pipeline?
A: Least-privilege tokens, OIDC, secret scanning, signed commits, pinned action versions (@v4), SAST/SCA/container scans, isolated agents, audit logs, protect main and workflow files.

Q18. What happens when a deployment fails mid-pipeline?
A: Depends on strategy: rollback script, revert Git manifest (GitOps), health-check failure triggers automatic rollback, or manual intervention. Idempotent deploy scripts and DB migrations need careful design.

Q19. Explain Jenkins controller vs agent.
A: Controller schedules jobs, serves UI, stores config. Agents execute steps on labeled nodes (Linux, Docker, K8s). Scaling = add agents; controller should not run heavy builds in production setups.

Q20. How would you design CI for a monorepo with frontend and backend?
A: Path filters (paths: in GitHub Actions) or tools (Nx/Turborepo) to run only affected packages; shared workflow templates; matrix for multiple apps; single artifact registry with per-service tags; optional merge queue for main.
